# Барьер и наборы шифров (в том числе ГОСТ)

Документ описывает, как Tuck шифрует данные в покое **на самом деле**, и как выбрать набор шифров.

## 1. Что именно делает барьер

```
root key  --(AEAD)-->  barrier key (DEK)  --(AEAD)-->  значения записей
```

- `root key` (32 байта) живёт только в памяти; его отдаёт seal (Shamir / auto-unseal / dev).
- **DEK один на всё хранилище**, а не по ключу на каждую запись. Он генерируется при инициализации, оборачивается `root key` и лежит в `barrier/keyring`.
- Ротация `root key` (`rekey`) перезаворачивает только DEK. Данные не перешифровываются. Сам DEK ротируется отдельно: `POST /v1/sys/rotate-data-key` создаёт новую версию ключа (новые записи шифруются ею, старые читаются прежним), с `?reencrypt=true` все записи перешифровываются, а старые ключи удаляются. Во время перешифрования барьер недоступен для чтения и записи. Keyring хранит все версии DEK; к шифртексту добавляется 4-байтовый номер версии. Для этого корневой ключ остаётся в памяти пока хранилище распечатано (как и сам DEK). Хранилища, созданные до версионирования ключей, ротацию DEK не поддерживают (409).
- Шифруется **значение** записи и (с метаданных версии 3) **путь** записи — см. §1.1. В хранилищах более ранних версий пути лежат в backend открыто.
- Каждое шифрование использует случайный nonce; формат записи `nonce || ciphertext || tag`.

### Привязка шифртекста к ключу (AAD)

Хранилища, созданные этой версией, подмешивают **путь записи как associated data** AEAD. Шифртекст, скопированный злоумышленником с доступом к диску из `secret/low` в `secret/high`, не расшифруется. Для `barrier/keyring` AAD — `barrier/keyring`.

Хранилища, созданные ранее, не имеют записи `barrier/meta`; они читаются как AES-256-GCM **без** AAD. Совместимость сохранена, перешифровывать ничего не нужно, но и защиты от подмены шифртекстов там нет.

### 1.1 Шифрование путей

Хранилища, созданные этой версией (`barrier/meta` версии 3), не хранят имена записей в открытом виде. Каждый сегмент пути (между `/`) заменяется на `base64url(nonce || AEAD(сегмент))`:

- `nonce` — HMAC от (родительский путь, сегмент): один и тот же ключ всегда даёт одно и то же хранимое имя (работают `Get`/`Put`/`Delete` и просмотр каталога), а имя обратимо (`List` показывает исходные имена);
- AAD — хранимый родительский путь, сегмент нельзя перенести в другой каталог;
- ключи шифрования и MAC для путей выводятся из отдельного `path_key` в keyring (не ротируется `rotate-data-key`; при `rekey` перезаворачивается вместе с keyring);
- префикс `barrier/` остаётся открытым — он нужен до распечатывания.

**Что скрыто:** имена записей. **Что не скрыто:** форма дерева, число записей, длины сегментов, совпадение сегментов под одним родителем, размеры значений.

`List(prefix)` использует полные сегменты префикса как хранимый префикс; неполный последний сегмент (`secret/a` для `secret/ab/...`) фильтруется после расшифровки, поэтому такой запрос сканирует весь каталог. Хранилища версий 1–2 (без `path_key`) продолжают работать с открытыми путями.

## 2. Наборы шифров

Выбор делается один раз при **первой** инициализации и записывается в `barrier/meta` (`{"version":3,"cipher":"..."}`; 1 — AAD по ключу, 2 — версионируемый keyring, 3 — шифрование путей). Изменить его у существующего хранилища нельзя; пока продуктивных хранилищ нет, миграция не нужна — при смене шифра создаётся новое хранилище.

| Имя | Алгоритм | Размер nonce | Примечание |
|---|---|---|---|
| `aes-256-gcm` (по умолчанию) | AES-256-GCM | 96 бит | стандартная библиотека Go |
| `gost-kuznyechik-mgm` | «Кузнечик» (ГОСТ Р 34.12-2015, RFC 7801) + MGM (RFC 9058) | 128 бит (старший бит обнуляется, nonce MGM — 127 бит) | собственная реализация, **не сертифицирована** |

Выбор:

```bash
tuck --barrier-cipher=gost-kuznyechik-mgm ...
# или в конфиге
barrier:
  cipher: gost-kuznyechik-mgm
```

Флаг действует только при создании нового хранилища; для существующего он игнорируется (набор берётся из `barrier/meta`).

## 3. Что такое «ГОСТ» здесь — и чем это НЕ является

**Реализовано:** «Кузнечик», MGM, Стрибог, KDF на HMAC-Стрибог — по тексту стандартов и RFC, проверены на опубликованных тестовых векторах. Код в `internal/gost/`, написан с нуля: готовые Go-библиотеки ГОСТ распространяются под GPLv3 и несовместимы с лицензией Apache-2.0.

**Не является:** сертифицированным СКЗИ. Для информационных систем, где закон или регулятор требует сертифицированную ФСБ России криптографию (КИИ, ГИС, банковская тайна и т. д.), подходит только сертифицированное средство — КриптоПро, ViPNet, Валидата и аналоги. Открытая реализация этого требования не закрывает.

**Как подключить сертифицированное СКЗИ:** `barrier.Suite` — это небольшая структура (имя, конструктор AEAD, флаг nonce). Новый набор регистрируется через `barrier.RegisterSuite` (например, обёртка над PKCS#11/CSP), после чего выбирается так же флагом `--barrier-cipher`. Корневой ключ при этом по-прежнему приходит из seal; для HSM-хранимого KEK нужен отдельный seal-бэкенд (см. TODO).

**Вопросы к ИБ банка до выбора:** какая модель угроз и класс защиты; требуется ли сертификат на СКЗИ; допустим ли «ГОСТ без сертификата» как дополнительный слой поверх сертифицированного канала/диска; кто держит ключи (HSM?).

## 4. Экспериментальные движки

PKI, SSH, TOTP, AWS, GCP и Azure выключены в бинарнике `tuck` по умолчанию (запросы к ним получают 404 `disabled`). Включение:

```bash
tuck --enable-engine=pki,totp
# или
enable_engines: [pki, totp]
```

При запуске печатается предупреждение со списком включённых экспериментальных движков. Причина: эти подсистемы шире, чем основная задача (доставка секретов в Kubernetes), и не прошли того же уровня проверки, что KV/Transit/Auth.

**Tuck не является корпоративным удостоверяющим центром.** Движок PKI выдаёт сертификаты от собственного CA для внутренних нужд (mTLS между сервисами, тесты). Он не заменяет УЦ банка: нет интеграции с аккредитованными УЦ, ГОСТ-сертификатов, HSM-хранения ключа CA, политик выпуска и отзыва уровня корпоративного PKI. Для промышленной выдачи сертификатов используйте корпоративный УЦ напрямую или cert-manager с ним; Tuck в этой схеме хранит только секреты.

## 4.1 Фокус пилота

Пилот ограничен: **KV v2 + Kubernetes auth + оператор `TuckSecret` (+ Injector при необходимости) + аудит**. Всё остальное (динамические секреты БД и облаков, PKI, SSH, TOTP) в пилот не входит, экспериментальные движки остаются выключенными.

## 5. Токены и namespace

Токен, выданный внутри namespace, привязан к нему: заголовок `X-Tuck-Namespace` с другим namespace даёт 403, без заголовка применяется namespace токена. Логины (Kubernetes/AppRole/JWT/GitHub/LDAP) получают namespace из поля роли `tuck_namespace`.

Если namespace, к которому привязана роль, удалён, логин по такой роли возвращает 403 (токен в «висящий» namespace не выдаётся).

### Раскатка привязки

1. Перечислите существующие роли (`GET /v1/auth/kubernetes/role/...`, аналоги для AppRole/JWT/LDAP) и для каждой решите целевой namespace.
2. Обновите роль, добавив `tuck_namespace` (`PUT` той же роли); новые логины сразу получают привязанный токен.
3. Уже выданные токены не меняются: дождитесь их истечения (TTL ролей) или отзовите (`POST /v1/auth/token/revoke`) — после этого привязаны все.
4. Проверка: токен роли с чужим `X-Tuck-Namespace` должен получать 403.

## 6. Известные ограничения собственной реализации ГОСТ

- Таблицы «Кузнечика» индексируются секретными данными, поэтому реализация **не константного времени** (возможна атака по времени кэша на хосте с чужим кодом). Для изолированного сервера Tuck риск ниже, чем для общего хоста, но это ещё одна причина предпочесть сертифицированное СКЗИ.
- Скорость: порядка 20 МБ/с на MGM — для секретов (килобайты) достаточно, для больших объёмов нет.
- Проверка — тестовые векторы RFC 7801, 9058, 6986, 7836; независимой криптографической экспертизы нет.
- Стрибог используется в Transit для HMAC (`hash_algorithm=streebog-256|512`), «Кузнечик»+MGM — как тип ключа Transit `kuznyechik-mgm`. KDF (`internal/gost/kdf`) реализован, но пока нигде не используется. Подпись ГОСТ Р 34.10-2012 не реализована (задача C6 в [12-bank-readiness-todo.md](12-bank-readiness-todo.md)).
