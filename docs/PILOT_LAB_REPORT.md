# Отчёт о прогоне пилотного стенда

[← Документация](README.md)

Версия: v2.1.0. Стенд собран на одной машине (Docker Desktop, Windows): это замер **функциональности и порядка величин**, а не заключение о производительности на серверном железе.

## Состав стенда

| Что | Как |
|---|---|
| Tuck | 3 узла Raft, Shamir 3 из 5, взаимный TLS между узлами, TLS для клиентов, образ собран из исходников |
| Балансировщик | HAProxy, проверка `GET /v1/sys/leader` (200 только у лидера), `X-Forwarded-For` + `trusted_proxies` |
| Каталог | OpenLDAP по `ldaps://` с собственным УЦ, служебная учётка только на чтение |
| SSO | Keycloak 25, клиент с PKCE, сертификат внутреннего УЦ |
| Kubernetes | два зеркальных кластера (minikube) `dc1` и `dc2`, Tuck вне кластеров |
| Данные | команда `payments`: 20 секретов (БД, Redis, Kafka, ключи JWT, платёжные системы и др.), 4 сотрудника в 3 группах; вторая команда `orders` |

| Подключение команды мастером: предпросмотр, создание, откат | работает |
| 20 секретов в Tuck, dc1 и dc2 (сверка по хэшам) | 20 из 20 совпали |
| Поды входят по ServiceAccount в каждом кластере; чтение 200, запись 403 | работает |
| Чужой ServiceAccount: 403; токен dc1 как токен dc2: 401 | отказ |
| Чужой namespace читает путь команды через TuckSecret | отказ оператора |
| Изоляция команд `payments` и `orders` в обе стороны | 403 |
| Ротация секрета доходит до Secret в обоих кластерах | 17–19 с при `refreshInterval` 30 с и кластере Tuck 2 из 3 |
| Потеря лидера Raft | перерыв записи около 8 с, потерь нет |
| Потеря узла (2 из 3) | запись и ротация продолжаются |

## Нагрузка (k6 через балансировщик, 20 секретов в хранилище)

| Сценарий | RPS | GET avg / p95 | PUT avg / p95 | Токен avg / p95 | Ошибки |
|---|---|---|---|---|---|
| до исправления, рост до 200 клиентов | 62 | 0,7 / 1 мс | 2,35 с / 4,97 с | 6,2 / 11,2 с | 0 |
| `load`, 50 клиентов | 626 | 0,9 / 2 мс | 78 / 144 мс | 249 / 507 мс | 0 |
| `stress`, до 200 клиентов | 889 | 1,2 / 3 мс | 106 / 197 мс | 315 / 578 мс | 0 |

Ресурсы: узел Tuck 54–59 МиБ RAM в покое, около 210 МиБ под нагрузкой, лидер до 37% одного ядра; HAProxy 22 МиБ.

## Что нашёл прогон (исправлено)

- Запись в Raft применялась по одной транзакции на запись: 62 RPS. Пакетное применение (`BatchingFSM`) дало 889 RPS.
- Лимиты запросов из флагов нельзя было поднять через `sys/config`, и настройка не доходила до других узлов.
- Оператор: ротация доходила за 60 с вместо 30 (скан попадал мимо только что обработанного ресурса).
- CSI тихо подменял секрет при одинаковом имени файла.
- Аудит не содержал имени человека; адрес клиента за балансировщиком был адресом балансировщика.
- LDAP: токен ушедшего сотрудника жил до конца срока.
- Независимое код-ревью нового кода: 14 замечаний, все исправлены (см. CHANGELOG 2.1.0).

## Что не проверено

- Независимый аудит безопасности не проводился.
- Сертифицированное СКЗИ и HSM: решение ИБ банка.
- Задержка между площадками: стенд на одной машине, сетевую задержку эмулировать не удалось.
- Вложенные группы Active Directory (проверено на OpenLDAP).
- Замена TLS-сертификата без рестарта и webhook-инжектор после последних доработок на стенде повторно не прогонялись (автотесты проходят).
- Релизный конвейер (goreleaser, cosign, SBOM) настроен; на реальном теге запускается впервые с релизом 2.1.0.
- Внедрений в эксплуатацию пока нет.
