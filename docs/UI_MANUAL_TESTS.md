## Ограничения тестового окружения

- **GitHub Actions OIDC** и **AWS/GCP/Azure dynamic secrets** — нет доступа к реальным внешним аккаунтам/раннерам, поэтому эти разделы ограничены UI-смок-тестом (CRUD форм), без сквозной проверки выдачи реальных кредов.
- **HA/Replication** — базовое окружение поднято как один под (`server.replicaCount: 1`, dev seal). Полноценная проверка HA/репликации потребует второй под с общим storage — помечено опциональным.
- **Shamir seal** — окружение использует `sealType: dev` (авто-распечатывание) для скорости итерации; ручное распечатывание через Shamir shares не входит в этот прогон (уже покрыто в `docs/MANUAL_TESTS.md` разделе 16).

### Найденные баги (сквозной список)

1. **`POST /v1/sys/rotate` всегда 500 для `sealType: dev`** — `internal/core/core.go:860` (`RotateKey`) вызывает `Dev.Init()` (`internal/seal/dev.go:32`), который отказывает при существующем файле ключа. Нужно либо отдельный метод ротации для Dev seal (перезаписать файл новым ключом), либо `RotateKey` не должен переиспользовать `Init()` для сидов, которые его не поддерживают в этом смысле.
2. **Dev-seal инстанс нельзя распечатать через UI после ручной «Печати»** — форма unseal в UI рассчитана только на Shamir-шард; для dev seal (0/0 шардов) нет альтернативного пути ввода. Либо скрывать кнопку «Печать» для dev seal в UI, либо добавить путь распечатывания для dev seal.
3. **[ВЫСОКАЯ ЗНАЧИМОСТЬ] Удалённый (и вообще любой не существующий) namespace остаётся полностью доступен через API** — `requireToken` (`internal/api/server.go:400-425`) читает заголовок `X-Tuck-Namespace` и кладёт его в контекст запроса **без какой-либо проверки, что такой namespace существует** (нет вызова `core.GetNamespace`). Итог: секреты, записанные в удалённом namespace, продолжают читаться; можно даже **создавать новые** секреты в namespace, который никогда не существовал или был удалён — просто отправив соответствующий заголовок с валидным токеном. Это прямо противоречит документированному поведению в коде (`internal/core/core.go:1708-1709`: «Secrets and policies stored within it remain in storage but become inaccessible until the namespace is recreated»). Нужно добавить проверку существования namespace в middleware (или в местах разрешения storage-префикса) и отклонять запросы с несуществующим/удалённым namespace (404/400).
4. **UI не даёт переключить активный namespace** — `setNamespace()` (`web/src/shared/auth/token.ts:20`) нигде не вызывается из компонентов дашборда, хотя вся инфраструктура для этого (localStorage + axios-заголовок) на месте. Функционально namespaces через веб-интерфейс неюзабельны за пределами страницы управления самими namespace-записями.
5. **[КРИТИЧНО] Любой непривилегированный токен полностью теряет сессию на стартовой странице дашборда** — цепочка:
   - Status-страница безусловно вызывает `GET /v1/sys/leases/?list=true` и `GET /v1/auth/token/?list=true` для счётчиков «Активность», без проверки прав и без деградации при отказе;
   - если у токена нет capability `list` на `sys/leases` и `auth/token` (что верно почти для любой реальной прикладной политики, кроме root/админской), бэкенд корректно отвечает 403;
   - но глобальный response-interceptor в `web/src/shared/api/axios.ts:30-38` реагирует на **любой** 401 **или 403** одинаково — эмитит `logoutEvents`, что стирает токен и разлогинивает.
   - Итог: воспроизведено вживую — создал токен с валидной, но ограниченной политикой (`secret/data/*` read/list), залогинился им → мгновенно выброшен обратно на экран логина при заходе на `/ui/dashboard/status` (стартовая страница после логина). **Веб-дашборд Tuck на практике пригоден только для root-токена** — любой сколько-нибудь ограниченный оператор не может им пользоваться вообще.
   - Исправление: не смешивать 401 (не аутентифицирован → разлогинить) и 403 (не авторизован для конкретного действия → показать toast/скрыть виджет, сессию не трогать); плюс сделать статус-виджеты Активности терпимыми к 403 (просто не показывать секцию/показывать «нет доступа» вместо краша сессии).
6. **Отсутствующая/удалённая политика в списке токена даёт 500, а не 403/400** — воспроизведено двумя разными путями: (a) создание токена с `policies:["default"]`, когда политики `default` ещё не существует — проходит без предупреждения (плейсхолдер формы создания токена сам подсказывает `default, read-only`, а в свежей установке политик нет вообще, `GET /v1/policy/?list=true` → `{"keys":[]}`); (b) обычное удаление политики через UI (Policies → корзина) без проверки, используется ли она живыми токенами. В обоих случаях последующий запрос этим токеном к защищённому пути падает `500 {"error":"resolve policies: policy \"...\": policy not found"}` вместо ожидаемого `403 permission denied`. Нужно: (1) на удаление политики — предупреждать/блокировать, если она attached к активным токенам/ролям, (2) на resolve — трактовать отсутствующую политику как «нет прав» (403), а не как внутреннюю ошибку (500).
7. **Quick-fill пресеты политик всегда используют одноуровневый путь `*`** (`web/src/pages/dashboard/policies/policies.page.tsx:139`) — при однозначно доказанной семантике glob (`internal/policy/policy.go:119-130`: `*` не пересекает `/`, только `**` рекурсивен), пресет **«Администратор»** не даёт доступа ни к чему вложенному — вводит в заблуждение относительно объёма выдаваемых прав. Стоит поменять шаблон на `'**'` либо явно указывать в UI разницу между `*`/`**`.
8. **[КРИТИЧНО] `tuck-operator` бесконечно крашлупится в любом стандартном Helm-деплое** (замечено попутно при подготовке LDAP-теста, детально относится к §18) — `deploy/helm/tuck/templates/operator/deployment.yaml:54-59` настраивает `livenessProbe` на `http://:8081/healthz`, но ни `cmd/tuck-operator/main.go`, ни пакет `internal/operator` **нигде не поднимают HTTP-сервер вообще** (grep по `8081|healthz|ListenAndServe` — 0 совпадений в non-test коде). Подтверждено вживую: под `tuck-operator` получил 21 рестарт за ~61 минуту (kubelet: «Liveness probe failed... connection refused» → убивает контейнер → чистый graceful shutdown по SIGTERM → рестарт → цикл). Контроллер успевает что-то реконсайлить в окне между рестартами (`operator: listed TuckSecrets count:0` в логах), но никогда не стабилизируется в `Ready`. Нужно либо реализовать `/healthz` на 8081, либо убрать/поправить пробу в чарте.
9. **[КРИТИЧНО] Helm-чарт не даёт tuck-server RBAC на TokenReview → Kubernetes auth не работает вообще из коробки** — `deploy/helm/tuck/templates/server/` содержит только `deployment.yaml`/`pvc.yaml`/`service.yaml`/`serviceaccount.yaml`, **RBAC-файла нет**. При этом сырой манифест `deploy/server/rbac.yaml` (альтернативный путь установки через `kubectl apply -f deploy/server/`) содержит ровно нужный `ClusterRole`+`ClusterRoleBinding` на `tokenreviews.authentication.k8s.io` — то есть это пробел именно в Helm-чарте, не в продукте в целом. Подтверждено вживую: реальный логин пода с ServiceAccount падал `{"error":"k8s token review: TokenReview: unexpected status 403"}` (`kubectl auth can-i create tokenreviews --as=system:serviceaccount:tuck:tuck-server` → no) до тех пор, пока не применил недостающий ClusterRole/Binding вручную — после этого login сразу заработал.
10. **LDAP и Kubernetes auth создают вечные токены при пустом TTL роли, без предупреждения** — `AppRole` (`internal/auth/approle/approle.go:228-230`), `JWT` (`internal/auth/jwt/provider.go:88-91`) и `GitHub Actions` (`internal/auth/github/github.go:120-121`) все безопасно подставляют `time.Hour`, если TTL роли ≤ 0. У `LDAP` (`core.go:1441` через `ldap.go:342-368`) и `Kubernetes` (`core.go:692`) такого фолбэка нет — TTL передаётся как есть, и `token.Generate` (`internal/token/token.go:61-63`) оставляет `ExpiresAt` нулевым, что по документированному контракту `IsExpired()` означает «никогда не истекает». Для Kubernetes это как минимум задокументировано в API (`internal/api/k8s.go:17`: `"" = never expires`), но **вводит в заблуждение сама форма UI**, которая показывает плейсхолдер «24h» — обычно плейсхолдер = дефолт при пустом поле, а по факту пустое поле означает вечный токен, а не 24 часа. Для LDAP такого предупреждения нет даже в коде. Воспроизведено вживую для обоих методов.
11. **KV v2: панель деталей секрета не инвалидирует кэш после записи новой версии** — `web/src/pages/dashboard/kv2/kv2.page.tsx` (WriteSecretForm) не приглашает React Query перезапросить открытую `SecretDetail` панель после успешной записи; воспроизведено вживую — записал версию 2, панель продолжала показывать "(v1)" и старое значение, пока не закрыл/открыл заново (backend при этом уже содержал верную версию 2).
12. **Дефолтный creation-statement для Postgres ломается на именах соединений с дефисом** — `internal/dynamic/database/database.go:44,234`: `DefaultCreationStatementsPostgres` использует `GRANT CONNECT ON DATABASE {{database}} TO "{{username}}"` — `{{username}}` в кавычках, а `{{database}}` **нет**; при этом `{{database}}` подставляется как `cfg.Name` (имя конфигурации соединения в Tuck), а не как реальное имя БД в Postgres. Итог: (a) имя конфигурации с дефисом (`qa-postgres` — абсолютно стандартная практика именования) даёт SQL syntax error; (b) даже без дефиса — если имя конфигурации не совпадает буквально с реальным именем базы данных, получаем `database "X" does not exist`, потому что нет отдельного поля «имя БД внутри Postgres», отличного от идентификатора соединения. Работает только если конфигурацию назвать точно как БД и без спецсимволов — случайное совпадение, не дизайн. Плюс: при 500 от `/v1/database/creds/{role}` UI не показывает вообще никакого уведомления об ошибке (молча ничего не происходит).
13. **[КРИТИЧНО — САМАЯ СЕРЬЁЗНАЯ НАХОДКА СЕССИИ] Отзыв lease через UI/generic API не удаляет реальную динамическую учётку — credential leak** — вкладка «Leases» в Dynamic Secrets (единственное UI-место для отзыва lease-ов от Database/AWS/GCP/Azure) вызывает `DELETE /v1/sys/leases/{id}` (`web/src/shared/api/endpoints/leases.ts:23`) → `core.LeaseManager().Revoke()` (`internal/api/leases.go:44`) — это **общий (generic) трекер lease-ов, который не вызывает специфичную для движка очистку** (для Database это `DROP USER` через `dbManager.RevokeLease`, доступный только по отдельному эндпоинту `DELETE /v1/database/lease/{id}`, `internal/api/server.go:319`; у AWS/GCP/Azure — аналогичная параллельная структура: `/v1/aws/lease/{id}`, и свои `Revoke{AWS,GCP,Azure}Lease` в core.go). Воспроизведено вживую от начала до конца: сгенерировал реальные Postgres-креды через UI, залогинился ими (`psql` подтвердил доступ), отозвал lease через `DELETE /v1/sys/leases/{id}` — API вернул 204 «успех», тост показал бы «отозвано», но **Postgres-пользователь остался активным** (`SELECT usename FROM pg_user` подтвердил присутствие после revoke и после паузы). Хуже того: после generic revoke запись lease пропадает из общего трекера, поэтому специфичный `DELETE /v1/database/lease/{id}` тоже возвращает 404 — **учётка становится навсегда неотзываемой через Tuck API**, требует ручного вмешательства DBA. Это подрывает саму суть Dynamic Secrets — единственный способ отозвать credential в UI создаёт иллюзию отзыва, оставляя реальный доступ открытым бессрочно.
14. **CSI-драйвер не обновляет смонтированные секреты никогда — только при пересоздании пода** — `internal/csi/driver.go` не содержит ни одного упоминания refresh/poll/rotation; секрет читается ровно один раз в `NodePublishVolume`. Подтверждено вживую: изменил значение в Tuck, подождал 40 секунд — файл в примонтированном томе остался старым. Это не баг сам по себе (многие secret-CSI-драйверы работают именно так по умолчанию), но создаёт несогласованность внутри одного продукта: Operator/TuckSecret CRD (§18) реализует честный live-refresh по `refreshInterval`, а CSI — нет вообще, и это несоответствие нигде не объяснено пользователю. Минимум стоит задокументировать явно («секреты через CSI статичны на весь срок жизни пода»), максимум — добавить `rotationPollInterval` по аналогии с Secrets Store CSI Driver.

## Заключение

Все 19 разделов чек-листа пройдены (плюс `HELM-3`/uninstall как финальное действие прогона), от auth-методов и KV v1/v2 до кластерных сценариев — Helm-чарта, Operator/TuckSecret CRD и CSI-драйвера — на реальном minikube-кластере, а не только smoke-тестами. Обнаружено 14 находок:

- **Критичные (5)**: #5 (401/403 conflation убивает сессию любого не-root токена), #8 (operator healthz crash-loop в любом Helm-деплое), #9 (Helm-чарт не даёт RBAC на TokenReview → Kubernetes auth не работает из коробки), #13 (generic revoke lease не удаляет реальную учётку — credential leak, самая серьёзная находка сессии).
- **Высокой значимости (1)**: #3 (доступ к удалённому namespace не блокируется).
- **Средние/низкие (8)**: #1, #2, #4, #6, #7, #10, #11, #12, #14 — баги UX/консистентности и краевые случаи (dev-seal rotate/unseal, переключение namespace в UI, resolve отсутствующей политики, quick-fill пресеты, вечные токены LDAP/K8s, KV v2 кэш, Postgres template, CSI vs Operator несогласованность).

Раздели чисто пройденные без находок: Token Roles (§4), KV v1 (§7), Response Wrapping (§9), Crypto Engines (§11), Mounts/Plugins/Cluster/Replication/Audit Sinks (§12–16), Operator+TuckSecret CRD (§18).

Тестовый кластер (minikube) деплой снесён (`helm uninstall`), CRD и PVC оставлены по политике Helm, ручной RBAC-патч и port-forward убраны за собой; сам minikube не остановлен.
