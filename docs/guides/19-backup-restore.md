# 19 — Backup и restore

[← Все гайды](README.md)

## Цель

Создать снимок данных Tuck и восстановить кластер после сбоя.

## Шаги

### 1. Snapshot (встроенный API)

В PowerShell `curl` это алиас `Invoke-WebRequest`, поэтому `curl.exe`; `-k` нужен для самоподписанного dev-сертификата.

```powershell
curl.exe -k "$env:TUCK_ADDR/v1/sys/snapshot" `
  -H "X-Tuck-Token: $env:TUCK_TOKEN" `
  -o tuck-snapshot.db
```

Потоковый дамп bbolt — работает на live-сервере (single-node file storage).

### 2. Проверить файл

```powershell
Get-Item tuck-snapshot.db | Select-Object Length, LastWriteTime
```

### 3. Restore (остановить сервер, заменить data file)

```powershell
# остановите процесс tuck
Copy-Item tuck-snapshot.db D:\tuck-data\tuck.db -Force
# запустите сервер снова
```

### 5. Raft HA: снимок и восстановление через API

В Raft-кластере данные лежат не в одном файле, поэтому замена файла не подходит. Снимок и восстановление делаются через API и CLI:

```bash
tuckcli snapshot save tuck-$(date +%F).snap        # скачать зашифрованный снимок (существующий файл не перезаписывается)
curl -X POST -H "X-Tuck-Token: $TOKEN" $TUCK_ADDR/v1/sys/cluster/snapshot   # снять снимок в каталог узла (последние 3)
```

Восстановление после потери кластера:

1. Поднимите пустой кластер из тех же образов (новые тома). Он сам инициализируется с **новыми** ключами и долями; root-токен и доли нового кластера нужны только на следующий шаг.
2. На лидере: `tuckcli snapshot restore tuck.snap --yes` (токен нового кластера). Без `--yes` команда отказывается: восстановление заменяет **все** данные кластера одной реплицируемой операцией.
3. Все узлы сами запечатываются: в снимке ключи старого кластера.
4. На каждом узле внесите **доли старого кластера** (`tuckcli --addr https://nodeN:8200 unseal <доля>` три раза). После этого вернутся root-токен, LDAP-конфигурация, роли, политики, namespace, секреты и токены **на момент снимка**.

Проверено: уничтожение трёх узлов и томов, пустой кластер, восстановление, распечатка старыми долями; 20 из 20 секретов совпали, LDAP-вход и операторы Kubernetes продолжили работу. Всё, что было записано после снимка, теряется: роль и токены после восстановления лучше пересмотреть. Ограничение: снимок восстанавливается одним Raft-сообщением, размер ограничен 256 МБ.

## Проверка

| Действие | Ожидаемый результат |
|----------|---------------------|
| snapshot файл | ненулевой размер |
| restore + unseal | `kv get` старых секретов работает |
| `GET /v1/health` | `"sealed": false` |

## Рекомендации

- Регулярные snapshot + off-site копия
- Тестируйте restore раз в квартал
- Root token после restore — из snapshot эпохи; планируйте ротацию
