01 — Текущая ситуация

Git + AES решает шифрование в покое. Не решает управление доступом

Хранить секреты зашифрованными в git — рабочий способ защититься от чтения репозитория посторонним. Он ничего не говорит о том, кто, когда и зачем эти секреты расшифровывал, и не даёт способа отозвать доступ, не тронув всё остальное.

01

Один ключ — весь доступ

AES-ключ для расшифровки обычно лежит в переменной окружения CI и доступен каждому пайплайну. Компрометация одного раннера — компрометация всех секретов организации.

02

История не забывает

Однажды закоммиченный секрет остаётся в истории git и после удаления файла. Полная очистка требует переписывания истории — рискованной операции для репозитория, на который завязаны CI и клоны команды.

03

Нет журнала обращений

git log показывает, кто закоммитил файл — не то, кто и когда его расшифровал и прочитал. Для внутреннего контроля и регуляторных проверок это принципиальная разница.

04

Ротация — ручной процесс

Смена скомпрометированного пароля к БД или облачного ключа — правки в нескольких местах вручную. Нет точки, которая сама выдаёт новый credential и отзывает старый.

При нескольких Kubernetes-кластерах в облаке риск множится: у каждого репозитория и пайплайна — свой AES-ключ и своя договорённость о его хранении. Единой политики доступа, охватывающей все кластеры сразу, при таком подходе не существует — она держится в памяти команды.

02 — Решение

Tuck: secrets manager, который живёт в вашем контуре

Один статический бинарник. Барьер AES-256-GCM с автоматическим unseal и разделением ключа по схеме Шамира. Без обязательной внешней БД. Разворачивается полностью в вашей инфраструктуре — без иностранного вендора, без облачной зависимости и без лицензионных ограничений на код (Apache-2.0).

03 — Функциональность

Что Tuck делает на практике

Хранение секретов

KV v1 / v2
Версионирование значений, история изменений, откат к прошлой версии.
Response wrapping
Одноразовая передача секрета — второй запрос на тот же токен уже не сработает.
TTL на версии
Автоматическая очистка устаревших версий по политике хранения.

Динамические секреты

PostgreSQL / MySQL
Короткоживущий credential по запросу, а не статичный пароль в манифесте.
AWS / GCP / Azure
Временные облачные ключи с автоматическим отзывом по истечении TTL.
Реестр lease
Принудительный revoke по API для любого выданного credential — без ожидания TTL.

Криптография как сервис

PKI
Корневой CA внутри Tuck, выпуск и отзыв сертификатов по роли.
Transit
Encrypt / decrypt / sign / verify — ключ никогда не покидает Tuck.
SSH CA
Подписанные SSH-сертификаты с TTL вместо статичных приватных ключей на серверах.
TOTP
Выпуск и проверка одноразовых кодов как отдельный сервисный движок.

Идентификация и доступ

6 auth-методов
Token, AppRole, LDAP, JWT/OIDC, GitHub, Kubernetes ServiceAccount (TokenReview).
Политики по путям
Доступ описывается на уровне конкретного пути, а не «весь секрет-стор целиком».
Audit log
Каждое обращение к секрету — кто, когда, к какому пути, с каким результатом.

Доставка в Kubernetes

Operator + CRD
TuckSecret живо синхронизируется в обычный Kubernetes Secret, без ручного sync.
CSI-провайдер
Секрет монтируется в под как том, без промежуточного Secret-объекта.
Terraform-провайдер
Секреты, политики и роли — как код, в том же пайплайне, что и инфраструктура.

Эксплуатация

HA-кластер
Репликация primary/secondary, добавление узла через отдельную роль join.
Без внешней БД
Один статический бинарник — меньше движущихся частей в проде.
Rotate / reseal
Смена root-ключа и повторное запечатывание барьера без даунтайма.

05 — Архитектура применения

Как это ляжет на вашу инфраструктуру

Один HA-кластер Tuck (несколько узлов, репликация) — центральная точка правды. В каждом Kubernetes-кластере — свой Operator и CSI-провайдер, которые синхронизируют нужные секреты локально; namespaces в Tuck разграничивают доступ между командами, средами и самими кластерами.

06 — Путь миграции

Без остановки текущих пайплайнов

Фаза 1

Импорт без изменения процессов

Существующие секреты переносятся из git в KV v2 через Terraform-провайдер или bulk-импорт CLI. Пайплайны продолжают работать, но читают значения из Tuck вместо расшифровки AES-блоба.

Фаза 2

Замена статичной аутентификации

CI/CD и workload'ы переходят на Kubernetes ServiceAccount или AppRole вместо общего ключа. Политики ограничивают каждый пайплайн только нужными путями.

Фаза 3

Динамические credentials

Статичные пароли к БД и облачные ключи заменяются движками Database/AWS/GCP/Azure — credential выдаётся на TTL и отзывается автоматически.

07 — Честно о зрелости

Что стоит знать до пилота

  • Один мейнтейнер на проекте. Прежде чем вводить Tuck в критичный контур, стоит закладывать время на code review силами вашей команды.
  • Внешнего security-аудита ещё не было. Код открыт под Apache-2.0 — ваша служба ИБ может проверить его сама, а не поверить на слово.
  • Публичных прод-инсталляций в банковском контуре пока нет. Разумный первый шаг — pilot на некритичном кластере, а не сразу весь периметр.
  • CSI-провайдер сейчас статичен. Секрет в томе обновляется при повторном монтировании; для live-обновления без пересоздания пода нужен Operator с CRD.

Открытый код — значит, ваша служба ИБ может проверить его сама.
